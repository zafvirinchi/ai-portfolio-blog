# Architecture Review Skill

This repository has accumulated real architectural decisions across 20 phases of work, several of them deliberately maintaining *two* parallel systems for the same-sounding concern (organization billing vs. platform billing; `recruiter/**` vs `recruitment/**`). The most common architecture mistake in this codebase's own history has been proposing something that already exists under a different name, or in the "other" parallel system. This skill exists to catch that before it happens again.

## The 9 questions — ask all 9 for any proposed new service/table/cache/engine

1. **Does an existing service already solve this?** Grep for the capability by concept, not just by exact name (e.g., searching only for "rate limit" would miss `job_match_requests`' IP-based rate limiting, `credit-service.ts`'s org-scoped usage limiting, and `entitlement-service.ts`'s quota system — three different existing mechanisms that could plausibly be confused with "add a rate limiter").
2. **Can an existing engine be reused?** For an AI feature specifically: is there already a generator in `src/lib/ai/**` that does this transformation on this input shape? This repo has 7+ separate LLM generator families (resume, LinkedIn, cover-letter, recruiter, recruitment, interview-prep, mock-interview) — a new feature that resembles one of these should extend it, not add an 8th.
3. **Does this introduce duplicate state?** Two tables/stores holding the same fact (e.g., a user's plan) is the exact shape of the org-billing/platform-billing split — that split was a deliberate, load-bearing decision made once, with its own extensive documentation (`PHASE18_MILESTONE1_BILLING_ENTITLEMENT_ARCHITECTURE.md`). A *new* instance of that shape, for a different concern, is almost certainly a mistake unless equally deliberate and equally documented.
4. **Does this introduce another source of truth?** Every plan/quota/feature-access fact in this repo has exactly one authoritative place (`platform-plan-registry.ts` for the platform system). A UI component computing its own copy of a limit, even for display only, is a duplicate source of truth — it must read the real value from the service response.
5. **Does this introduce unnecessary LLM calls?** Many features in this repo are deliberately deterministic/zero-cost (ATS scoring's sub-components, ranking, ATS explainability, ranking/SEO/profile-score computation) specifically because the task doesn't need model reasoning. A new feature reaching for an LLM call where a deterministic computation would produce an equally correct, cheaper, faster, and more debuggable result should be challenged.
6. **Does this introduce additional persistent data?** This repo already has 15 migrations and no migration tooling (manual SQL Editor application) — a new table is a real, non-trivial operational cost (another manual step in every environment's activation runbook), not a free architectural choice. Prefer extending an existing table's shape (an additive column, a JSONB field like `recruiter_candidates.decision_history`) over a new table, when the data genuinely belongs to an existing entity.
7. **Does this weaken ownership/security?** Does the new design still filter by the resolved owner at the query layer? Does it still resolve identity server-side? A new architecture that makes ownership checking *harder* to get right consistently (e.g., a shared cache keyed by something other than the full ownership tuple) is a regression even if functionally correct today.
8. **Does this increase operational complexity?** New infrastructure (a queue, a cache layer, a second migration tool, a rate limiter) has a real activation/maintenance cost this repo has repeatedly, explicitly chosen to avoid (see the standing "no speculative Redis/rate-limiting infrastructure" instruction that recurs across the Phase 19-20 audit reports). The bar for adding new infrastructure is "a demonstrated, evidenced need," not "would be nice to have."
9. **Is the change actually required?** Distinguish a genuine defect (proven by a failing test, a reproducible bypass, or a live-probed incorrect response) from a speculative improvement. This repo's own established discipline (visible across 20+ `PHASE*.md` audit reports) is to fix proven defects minimally and defer everything else with a documented reason — match that discipline.

## Structural areas to review

- **Module/service boundaries**: one `*-service.ts` per concern, route handlers stay thin. A route with business logic inlined (more than parsing + auth + one service call + response shaping) is a boundary violation.
- **AI/LLM architecture**: `src/lib/ai/openai.ts` (the one metered client) → LangChain/LangGraph for the multi-agent chat graph (`src/lib/ai/graph/**`, `src/lib/ai/multi-agent/**`) → per-feature generator files. A new LLM call site should go through the existing metered client, not construct a second `OpenAI`/`ChatOpenAI` instance.
- **Agent orchestration**: the chat graph is a strict, acyclic `StateGraph` (`START → planner → [tool?] → promptBuilder → generation → END`). A new node must not introduce a cycle or a path that reaches `generation` (and therefore an LLM call) without passing through the planner's own routing.
- **RAG architecture**: `chromadb` + `src/lib/ai/ingestion/**`/`src/lib/ai/knowledge/**` for the portfolio/interview-question knowledge base. This is a separate concern from the per-feature generators — don't conflate RAG retrieval with a feature's own structured generation.
- **Deterministic vs. LLM responsibilities**: see question 5 above. Look for a `compute*`/`*-engine.ts`/`*-score.ts` file already solving the sub-problem before assuming it needs a model call.
- **Persistence vs. ephemeral state**: the ephemeral, in-memory, TTL-`Map` pattern (resume-rewriter, mock-interview, interview-prep, LinkedIn, cover-letter) is deliberate for session-scoped, non-durable product flows. Resume Versions, recruiter candidates/jobs, and everything platform/organization-billing-related is genuinely Supabase-persisted. Don't persist something that's supposed to be ephemeral (adds migration/operational cost for no product benefit), and don't make something ephemeral that users expect to survive a page reload days later.
- **Caching / request-scoped memoization**: the only cache in this system (`withEntitlementCache()`, `AsyncLocalStorage`-based) is explicitly request-scoped — fresh per call, never module-global, never cross-request, never cross-user. Any new caching proposal must be justified by the same kind of evidence that motivated this one (a measured, repeated Supabase query fan-out), not speculative.
- **Background processing**: none exists in this repo (no queue, no worker, no cron) — every operation is synchronous within a single request/response cycle. A proposal requiring background processing is a significant architectural addition needing explicit sign-off, not something to introduce incidentally.
- **Coupling / circular dependencies**: check that a new file in `src/lib/ai/<feature>/` doesn't import from an unrelated feature's directory directly (cross-feature reuse should go through a clearly-named shared utility, not a direct import of another feature's internal service).
- **Failure isolation**: does a new integration follow the established "fail open on logging/usage-lookup, fail closed on entitlement decisions" asymmetry? A Supabase read failure for a *paid-access* fact must never silently grant paid access; a Supabase read failure for a *usage count* should degrade to zero rather than blocking the feature.

## Output format

For a proposed architectural change, answer all 9 questions explicitly (a one-line answer is fine when the answer is clearly "no issue"), then give a single recommendation: **PROCEED**, **PROCEED WITH CHANGES** (name them), or **DO NOT PROCEED — REUSE <existing thing> INSTEAD** (name the existing thing and where it lives).
